# 0. このドキュメントの位置づけ

本ドキュメントは `prd.md`（プロダクトビジョン・体験設計）を**置き換えるものではなく補完するもの**である。

Claude Codeは実装着手時に、以下の順で両方を読み込むこと。

```text
1. prd.md              → プロダクトの「なぜ」「何を」
```

prd.mdとこのドキュメントが矛盾する場合、**体験設計はprd.mdを優先し、技術的な実現方法・制約はこのドキュメントを優先する**。

このドキュメントが対象とする欠落領域：

- 具体的な技術選定と選定理由

- API/DB設計規約
- テスト・CI/CD
- 監視・ロギング
- 法務・プライバシー

# 1. 大前提：無料の範囲で「公開まで」できること

**最重要制約。** このプロジェクトは個人開発規模で、原則すべてのインフラを無料枠内で完結させる。

Claude Codeは技術選定時に、必ず各サービスの無料枠上限を明示し、それを超えないアーキテクチャを設計すること。「後で有料化すればいい」という前提で無料枠を無視した設計をしてはならない。

## 1.1 唯一の例外：LLM API

**AI Mentor機能で使うLLM APIだけは、原則として無料では完結しない。** これはprd.mdでは前提とされていないため、ここで明示する。

Claude Codeは以下のいずれかの方針を実装すること。ユーザー（プロダクトオーナー）に選択させる形でもよい。

```text
方針A: 無料枠のあるLLMを使う
  - Google Gemini API（無料枠あり、レート制限あり）
  - Groq API（無料枠あり、レート制限あり）
  - ローカルLLM不採用（ホスティング環境的に非現実的なため除外）

方針B: 有料LLM（Anthropic API等）を使うが、厳格な予算上限を設ける
  - 1ユーザー1日あたりのAIメンター利用回数に上限（例: 20回/日）
  - 月額予算上限をハードコードし、超過時はAI Mentorを
    「今日はお休み中」として静的フォールバックに切り替える
  - トークン数の少ないプロンプト設計（Quest文脈は要約して渡す）
  - キャッシュ可能な応答（同じヒントは再生成しない）はキャッシュする
```

いずれの方針でも、**AI APIキーの利用量を可視化するダッシュボード（簡易でよい）と、予算超過時のグレースフルデグラデーション（機能停止ではなく代替UX）を実装すること。**

## 1.2 推奨無料枠構成

| レイヤー | サービス | 無料枠の目安 | 備考 |
|---|---|---|---|
| Hosting / Frontend | Vercel (Hobby) | 個人利用は無料、商用利用不可の規約に注意 | 商用化する場合はProプラン検討を注記 |
| DB / Auth | Supabase (Free) | DB 500MB、月間アクティブユーザー数に上限あり | 一定期間操作がないと一時停止（Pause）される点に注意し、定期pingや案内UIを検討 |
| SQL実行環境 | DuckDB-Wasm（ブラウザ内実行） | サーバーコスト0 | 詳細は5章参照。サーバー実行より優先すべき理由あり |

| レート制限用ストア | Upstash Redis (Free) | コマンド数/月に上限あり | サーバーレス環境で分散カウンタが必要なため導入。詳細は4.3節 |

| LLM API | 1.1節参照 | 無料では完結しない前提 | |

# 2. 技術スタック確定方針

prd.md §67の候補をベースに、以下を確定方針とする。理由もdocs/architecture.mdに記載すること。

```text
Frontend    : Next.js (App Router) + TypeScript + Tailwind CSS
State       : React Server Components基本、必要な箇所のみクライアント状態管理
              （軽量なもの: zustand等。Redux等の大掛かりな導入は不要）
Backend     : Next.js Route Handlers / Server Actions（別バックエンド不要）
DB          : PostgreSQL（Supabase経由）
ORM         : Prisma（マイグレーション管理・型安全性のため推奨）
Auth        : Supabase Auth（Email/Password + OAuth任意）
SQL実行     : DuckDB-Wasm（クライアントサイド実行、詳細5章）
Editor      : Monaco Editor
AI          : LLM APIをサーバー側（Route Handler）経由で呼び出す。
              クライアントに直接APIキーを渡さない
Deployment  : Vercel
Package Mgr : pnpm（インストール高速化・ディスク節約のため）
Node        : LTSバージョンを`.nvmrc`または`package.json engines`で固定
Rate Limit  : Upstash Redis（サーバーレス環境向け分散レート制限、詳細4.3節）
```

Claude Codeがこの構成を変更する場合は、無料枠制約・実装容易性・保守性の観点で理由を明記すること。

## 2.1 DBコネクション管理（サーバーレス特有の注意点）

**重要な技術的落とし穴。** Next.jsをVercel（サーバーレス）上で動かす場合、リクエストのたびに関数インスタンスが起動し、素朴にPrismaでPostgresへ直接接続すると同時接続数がSupabase無料枠の上限をすぐに超え、`too many connections`エラーが発生しやすい。

対策として以下を必須とする。

```text
- Supabaseが提供するTransaction Pooler（PgBouncer経由）の接続文字列を使用する
  （直接接続用のURLとPooler用のURLは別物なので混同しない）
- Prismaの`schema.prisma`で`directUrl`（マイグレーション用・直接接続）と
  `url`（アプリ実行時・Pooler経由）を分けて設定する
- コネクションプールのサイズ上限をPrisma側でも明示的に設定し、
  無料枠のPostgres最大接続数を超えないようにする
```

Claude Codeは初期セットアップの段階でこの設定を行い、`docs/architecture.md`に接続方式の図解を残すこと。

## 3.1 Questコンテンツの管理方針（prd.md §69, §70の具体化）

- MVPではQuestコンテンツを**DBではなくリポジトリ内のJSONファイル**として管理する（`content/quests/*.json`）。理由：DB無料枠の節約、Gitでのレビュー・差分管理のしやすさ、将来のQuest Packの追加容易性。
- 起動時またはビルド時にJSON Schemaでバリデーションを行い、不正なQuestファイルがあればビルドを失敗させる。
- ユーザーの進捗・履歴（`quest_attempts`等）はDBに保存する。Questの静的コンテンツと、ユーザーの動的な状態を明確に分離する。

## 3.2 環境変数

- `.env.example`を必ず用意し、必要な環境変数とその説明をコメントで記載する。
- 実際の値（APIキー等）は絶対にリポジトリにコミットしない。`.gitignore`で`.env*`（`.env.example`除く）を除外する。
- Vercelの環境変数機能でProduction/Preview/Developmentを分離する。

## 3.3 ローカル開発環境構築

新規参加者（将来的な共同開発者を含む）が迷わずローカル環境を立ち上げられるよう、READMEに以下のクイックスタート手順を用意する。

```text
1. Supabase CLIをインストールし、`supabase start`でローカルSupabase
   （Postgres + Auth + Storage）をDocker上に起動する
   （本番のSupabaseプロジェクトを直接ローカル開発に使わない。
   　無料枠消費・データ事故防止のため）
2. `.env.example`を`.env.local`にコピーし、ローカルSupabaseが払い出す
   接続情報を設定する
3. `pnpm install`
4. `pnpm prisma migrate dev`でローカルDBにスキーマを反映
5. `pnpm db:seed`でQuestコンテンツ・開発用ダミーユーザーを投入
6. `pnpm dev`で開発サーバー起動
```

- ローカル環境ではAI Mentorの呼び出しをモック（固定レスポンス返却）に切り替えられるフラグ（例: `AI_MENTOR_MOCK=true`）を用意し、開発中にLLM APIコストが発生しないようにする。
- DuckDB-Wasmはローカル/本番の差異がほぼ発生しない想定だが、COOP/COEPヘッダー（5.1節参照）はローカル開発サーバーでも同様に設定し、本番と挙動を揃える。

# 4. セキュリティ要件

## 4.1 ユーザーコード実行のサンドボックス（最重要）

prd.md §62で「安全なsandbox環境」とだけ書かれているが、これを以下のように具体化する。

**方針：ユーザーが書いたSQL/Pythonをサーバー側で直接実行しない。**

```text
理由:
- サーバー側実行は、リソース枯渇・無限ループ・悪意あるコードによる
  他ユーザーへの影響リスクがある
- 無料枠のサーバーリソースでは、実行時間制限・プロセス分離を
  安全に実装するコストが高い
```

MVPでの推奨実装：

- SQL: **DuckDB-Wasmをブラウザ内で実行する。** ユーザーのコードはユーザー自身のブラウザサンドボックス内でのみ実行され、他ユーザー・サーバーに影響しない。実行結果の判定（成功/失敗）もクライアント側で行い、達成記録のみサーバーに送信する。
- Python/PySpark（将来拡張、MVP外）: 実装する場合はPyodide（ブラウザ内Python実行）を優先候補とし、サーバー側でのコード実行は避ける。どうしてもサーバー実行が必要な場合は、実行時間・メモリ・ネットワークアクセスを厳格に制限したコンテナ環境（例: 使い捨てコンテナ、ネットワーク遮断）を用いること。

- **クライアント側実行結果をそのまま信頼しない。** XP付与やMastery更新など「報酬」に関わる判定は、最低限のサーバー側検証（例: 送信された結果が期待されるスキーマ・妥当な範囲か）を挟む。ただし過度なアンチチート実装はMVPでは不要（悪意ある個人利用の被害が小さいため）。

## 4.2 認証・認可

- Supabase AuthのRow Level Security (RLS) を全テーブルに設定し、「自分のデータしか読み書きできない」ことをDBレベルで保証する。アプリケーション層のチェックのみに依存しない。
- セッション管理はSupabase Authの標準機構（Cookieベースのセッション、リフレッシュトークンによる自動更新）に従う。セッション有効期限はSupabase Authのデフォルト設定を基本とし、変更する場合は理由をdocs/architecture.mdに残す。

### 4.2.1 サインアップ・メール確認フロー

- 新規登録時はメールアドレス確認（confirmation email）を必須とする。未確認ユーザーはQuestの進捗保存等、DB書き込みを伴う機能を制限し、「メールを確認してください」という状態を明確にUI表示する。
- 確認メール・パスワードリセットメールは、**Supabase標準のメール送信機能ではなく外部トランザクションメールサービス（Resend等の無料枠）経由で送信する**（1.2節参照）。Supabase標準機能は無料枠での送信数上限が非常に低く、ユーザー増加時に認証フロー自体が破綻するリスクがあるため。

### 4.2.2 パスワードリセット

- 「パスワードを忘れた」導線を用意し、Supabase Authのパスワードリセットトークン機構を利用する。
- リセットリンクの有効期限、ワンタイム性（一度使用したら失効）はSupabase Authの標準挙動に従う。

### 4.2.3 OAuth（任意実装）

- OAuthプロバイダを追加する場合はGoogleを優先候補とする（対象ユーザー層の利用率が高いため）。
- 取得スコープは必要最小限（メールアドレス・表示名程度）に絞り、不要な権限を要求しない。

### 4.2.4 不正アクセス対策

- ログイン試行に対するレート制限（例: 同一メールアドレス/IPからの短時間の連続失敗をブロック）をSupabase Auth標準機構またはUpstash Redisベースの実装で行い、ブルートフォース攻撃を防ぐ。
- 退会（アカウント削除）機能を実装する場合は、削除リクエスト受付後にメール等での再確認を挟むか、一定期間の猶予（例: 復元可能期間）を設けるかを検討する。誤操作による即時完全削除は避ける。

### 4.2.5 認可（RLS以外の考慮点）

- RLSに加えて、Server Actions/Route Handler側でも「リクエストしたユーザーIDと対象リソースの所有者が一致するか」を確認するアプリケーション層のチェックを二重に行う（多層防御）。RLSだけに依存すると、RLSポリシー設定ミス時に単一障害点になる。

## 4.3 AI Mentorエンドポイントの保護

- **レート制限の実装方式：Upstash Redis（無料枠）を使ったユーザーID単位のカウンタ**を実装し、無料枠APIコストの暴走を防ぐ。Vercelのサーバーレス関数はインスタンスごとにメモリが分離されるため、アプリケーションのメモリ内カウンタ（単純なグローバル変数等）ではレート制限が機能しない点に注意すること。
- 制限値は1.1節の予算方針（1ユーザー1日あたりの利用回数上限）と連動させ、Redis側のカウンタが日次でリセットされるようTTLを設定する。
- プロンプトインジェクション対策：Questコンテンツ（将来的にユーザー投稿の可能性がある場合）やユーザー入力をシステムプロンプトに埋め込む際は、ユーザー入力がAIの指示を上書きできないよう明確に区切る。
- AIへの入力に含める個人情報を最小化する（prd.md §71で言及されている「不要な個人情報を渡さない」の具体化：氏名・メールアドレス等はAIコンテキストに含めず、ユーザーIDやスキル状態など匿名化可能な情報のみ渡す）。
- AI Mentorとの会話（`ai_conversations`テーブル）は保持期間を定め（例: 90日）、それを超えたものはバッチ削除するか要約のみ残す。会話ログにはAI Mentorの応答生成に使ったコンテキスト（Quest ID、スキル状態等）も含まれうるため、8章のプライバシー要件と合わせて保持方針をプライバシーポリシーに明記する。
- ストリーミング応答（Server-Sent EventsまたはVercel AI SDKのstreaming）を採用し、AI応答の体感速度を上げる。ストリーミング中にエラー・タイムアウトが発生した場合のフォールバック表示（12章の世界観に沿ったエラーメッセージ）を用意する。

## 4.4 一般的なWebセキュリティ

- 入力バリデーションはサーバー側でも必ず行う（クライアント側バリデーションのみに依存しない）。バリデーションライブラリとして`zod`を推奨。
- 主要なセキュリティヘッダー（CSP, X-Frame-Options等）をNext.jsのmiddlewareまたは設定で付与する。
- 依存パッケージの脆弱性は`pnpm audit`等をCIに組み込んで定期チェックする。

# 5. DuckDB-Wasm採用の理由（補足）

prd.md §62では「DuckDB / PostgreSQL等」が並列候補として挙がっているが、以下の理由からMVPでは**DuckDB-Wasm（クライアントサイド）を第一候補とする**。

```text
- サーバー実行コストがゼロ（無料枠の消費なし）
- ユーザーごとの実行環境が自然に分離される（サンドボックスの単純化）
- 同時アクセス数が増えてもサーバー負荷にならない
- オフラインでも動作可能
```

デメリット（Claude Codeが把握しておくべき点）：

```text
- 初回ロード時にWasmバイナリのダウンロードが発生する（バンドルサイズに注意）
- 非常に大きなデータセットを扱うQuestには不向き
  （MVPのQuestは学習用の小規模データセットなので問題にならない想定）
```

## 5.1 ブラウザ要件（COOP/COEPヘッダー）— 重要な技術的制約

DuckDB-Wasmのマルチスレッド版は`SharedArrayBuffer`を利用するため、以下のレスポンスヘッダーが必要になる。

```text
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

これをNext.jsの`next.config.js`またはmiddlewareでアプリ全体に設定する。ただしこの設定には副作用があり、Claude Codeは以下を把握した上で導入すること。

```text
- 上記ヘッダーを設定すると、CORP（Cross-Origin-Resource-Policy）ヘッダーを
  持たない外部リソース（一部の外部埋め込みスクリプト、画像CDN等）の
  読み込みがブロックされる場合がある
- Analyticsスクリプトや将来のOAuthポップアップ連携を追加する際は、
  この制約と衝突しないか事前に確認する
- シングルスレッド版のDuckDB-Wasmを使えばこの制約を回避できるが、
  実行速度が落ちるトレードオフがある。MVPの小規模データセットで
  あればシングルスレッド版で十分な可能性があり、まずシングルスレッド版
  から検討し、パフォーマンス上の必要が出た場合のみマルチスレッド版へ
  移行することを推奨する
```

## 5.2 実環境接続との関係

Databricks実環境との接続（prd.mdで「後段」とされている機能）を将来実装する際は、別途サーバー側の認証・接続管理が必要になる点をdocs/architecture.mdに記載しておくこと（詳細は6章）。

# 6. プラットフォーム実環境接続フェーズ（Databricks / Snowflake）

## 6.1 前提：MVPは「概念学習」であり「プロダクト操作の習熟」ではない

5章の通り、MVPのQuestはDuckDB-Wasm上で実行される。これはコスト・セキュリティ面で正しい判断だが、副作用として **MVPだけでは実際のDatabricksワークスペースやSnowflakeコンソールの操作スキルは身につかない**。ユーザーが学べるのは以下の範囲にとどまる。

```text
MVPで学べること:
- SQLでの問題解決力（JOIN、集計、Window関数等）
- データ基盤の考え方（Bronze/Silver/Gold、Job失敗の調査手順等）
- Databricks/Snowflakeの用語・ワークフローの疑似体験（ストーリー上の文脈として）

MVPで学べないこと:
- 実際のDatabricksワークスペースUI操作
- Unity Catalog、Lakeflow Connect、Auto Loader等の実機設定
- Snowflakeの実際のWarehouse管理・コンソール操作
- 実データ量でのパフォーマンスチューニング感覚
```

この区別をユーザーに対しても誤解のないように示すこと。例えば、Quest内やPlatform選択画面で「これは実際のDatabricksを操作するQuestではなく、Databricksの仕事を疑似体験するQuestです」といった説明を、prd.mdのNo Shame UX/Reality Check原則（§76）に沿ったトーンで自然に伝える。ユーザーが「アプリを卒業すれば即戦力」と誤認しないようにする。

## 6.2 実環境接続を後続フェーズとして設計する理由

実環境接続をMVPに含めない理由は、単に「後回し」ではなく無料枠制約と直結する。

```text
- Databricks / Snowflakeの無料トライアルは期間限定（例: 14日間）であり、
  常設の学習環境として組み込むには継続的なコストが発生する
- ユーザーごとに実環境のクレデンシャルを安全に管理する仕組み
  （Secrets管理、OAuth連携等）が必要になり、セキュリティ・運用コストが増す
- 実環境への接続はAPIコール課金や実行時間課金が発生しうるため、
  1章のAI API同様に「無料では完結しない」領域になる
```

そのため、実環境接続は**明確に別フェーズ（Post-MVP）として切り出し、MVPの設計がそれを阻害しないようにする**、という位置づけにする。

## 6.3 MVP時点で仕込んでおくべき設計（Platform Adapter抽象化）

後から実環境接続を追加する際に大規模な作り直しが発生しないよう、MVPの時点で以下の抽象化だけは行っておく。

```text
lib/platform-adapter/
├── types.ts          # PlatformAdapterインターフェース定義
│                        (execute(sql), listTables(), getSchema() 等)
├── duckdb-adapter.ts  # MVPの実装（DuckDB-Wasm）
└── (将来) databricks-adapter.ts
    (将来) snowflake-adapter.ts
```

- Quest実行ロジックは`PlatformAdapter`インターフェースに対してのみ依存させ、DuckDB-Wasmの実装詳細に直接依存させない。
- Questコンテンツ（JSON）には`platform: "duckdb" | "databricks" | "snowflake"`のようなフィールドを持たせておき、将来的に同じQuestを複数実行環境で提供できるようにする（ただしMVPでは`duckdb`のみを使用）。
- この抽象化はあくまで「将来の拡張を阻害しない」程度にとどめ、Post-MVPの機能を先行実装しない（2章のDo not overengineer原則に従う）。

## 6.4 Post-MVPでの実環境接続の実装方針（案）

将来フェーズとして着手する際の方針をあらかじめ記録しておく。

```text
- ユーザー自身のDatabricks/Snowflakeアカウント（トライアルアカウント含む）に
  接続する「Bring Your Own Account」方式を基本とする
  （運営側が実行コストを負担する共有環境は無料枠と相性が悪いため）
- 接続情報（Personal Access Token等）は暗号化してDBに保存するか、
  セッション内のみ保持しサーバーに永続化しない設計を検討する
- Capstone Project（prd.md §38）や卒業条件（prd.md §37）の一部として、
  「実環境に接続して1つのQuestをクリアする」を組み込むことで、
  DuckDB-Wasmでの疑似体験から実機操作への橋渡しにする
```

Claude CodeはPost-MVPフェーズに着手する際、このセクションを起点にあらためて要件定義を行うこと。MVPフェーズではこの節の内容を実装する必要はない。

# 7. データベース設計規約

prd.md §68のテーブル一覧を土台に、以下の規約を追加する。

- 全テーブルに `id (uuid, PK)`, `created_at`, `updated_at` を基本カラムとして持たせる。
- 外部キー制約を明示的に張り、参照整合性をDBレベルで保証する。
- 頻繁に検索条件になるカラム（`user_id`, `quest_id`等）にはインデックスを張る。
- マイグレーションはPrisma Migrateで管理し、`prisma/migrations/`に履歴を残す。手動でのスキーマ変更（Supabaseダッシュボードからの直接編集）は禁止し、必ずマイグレーションファイル経由で変更する。
- ユーザー削除時のデータ扱い（退会機能を実装する場合）：関連する学習履歴は匿名化のうえ保持するか完全削除するかを、8章のプライバシー要件と合わせて決定する。

## 7.1 バックアップ・ディザスタリカバリ

**重要。** Supabase無料枠ではPoint-in-Time Recovery（任意時点への復元）が利用できない。ユーザーの学習進捗・XP・Mastery等はプロダクトの根幹データであり、消失した場合の影響が大きいため、以下を実装する。

```text
- GitHub Actionsの定期実行（cron）で、`pg_dump`による
  DBエクスポートを定期的（例: 週1回）に取得する
- エクスポートしたバックアップは、リポジトリとは別の保管先
  （例: 無料枠のあるオブジェクトストレージ、またはGitHub Actionsの
  Artifacts機能）に保存する。保管期間・世代管理方針も決める
- 手動でのリストア手順をdocs/architecture.mdに文書化しておく
  （実際に試したことがない手順は無いのと同じなので、
  可能であれば一度リストアをリハーサルする）
```

## 7.2 冪等性・同時実行制御

- Quest submitやXP付与など「報酬」に関わる書き込みは、二重送信（連打・リトライ）によって重複付与されないよう、リクエストごとに一意なキー（例: `attempt_id`）を発行し、同一キーでの再送信は既存結果を返すだけにする（冪等性の担保）。
- 同一ユーザーの同一Questに対する同時多重リクエスト（複数タブでの同時操作等）を考慮し、DBレベルでのユニーク制約または楽観的ロック（`updated_at`の比較等）で競合を検出する。

## 7.3 デイリー処理・タイムゾーンの定義

prd.mdのDaily Quest（§19）、Streak（§20）は「日が変わったかどうか」の判定に依存するが、基準タイムゾーンが未定義だと日本のユーザーにとって直感に反する挙動（例: 深夜0時台の利用でStreakが正しくカウントされない）が起きうる。

- **本アプリの「1日」の境界は日本時間（JST, UTC+9）の午前0時を基準とする**ことを明示的に定義する。
- サーバー側のロジック・DBに保存する日付は原則UTCで保持しつつ、Daily Quest/Streakの判定ロジックのみJSTに変換して計算する。
- 将来的に海外ユーザーを想定する場合でも、MVPではJST固定とし、ユーザーごとのタイムゾーン設定は導入しない（複雑化を避けるため）。

# 8. 法務・プライバシー要件

prd.mdには一切言及がないが、**公開する以上は必須**の要件として追加する。想定ユーザーは日本語話者・日本国内在住者が中心のため、**GDPR的な一般論ではなく、日本の個人情報保護法（APPI）を基準とした対応**を行うこと。海外ユーザーの利用も想定する場合は、その時点で追加対応（GDPR等）を検討する。

- 公開前に以下のページを最低限用意する：
  - プライバシーポリシー（個人情報保護法に基づく利用目的の明示、収集する情報、AI API（外部事業者）への送信有無、Cookie利用有無、第三者提供の有無を明記）
  - 利用規約
  - 特定商取引法に基づく表記（有料機能を将来追加する場合）
- 個人情報の保存先がSupabase等の海外リージョンにある場合、越境移転に該当しうる点をプライバシーポリシーに記載する（保存先リージョンを確認し、可能であれば東京リージョンを選択する）。
- Analyticsやエラートラッキングツールを使う場合、収集する情報の範囲をプライバシーポリシーに反映する。
- ユーザーが自分のデータのエクスポート・削除を要求できる導線を用意する（簡易的なものでよいが、存在は必須。個人情報保護法上の開示・削除請求対応の簡易版として位置づける）。
- 未成年ユーザーの利用を想定するかどうかを明確にし、想定する場合は保護者同意等の要否を検討する。

# 9. API / サーバーアクション設計規約

- Server ActionsとRoute Handlersの使い分け基準：
  - フォーム送信・単純なミューテーション → Server Actions
  - 外部からの呼び出しが必要、または細かいHTTPステータス制御が必要 → Route Handlers
- エラーレスポンスは統一フォーマットを用いる：

```json
{
  "error": {
    "code": "QUEST_NOT_FOUND",
    "message": "指定されたQuestが見つかりません"
  }
}
```

- 全ての外部入力（フォーム、APIリクエストボディ）は`zod`スキーマでパースしてから処理する。
- 将来的な後方互換性のため、Route Handlerには`/api/v1/`のようにバージョンプレフィックスを付ける。

# 10. テスト戦略

各Phase終了時にprd.md §80で「lint / typecheck / tests / build」が求められているが、具体的な実装方針を追加する。

```text
Unit Test       : Vitest
                  対象: Mastery計算ロジック、XP計算ロジック、
                  Quest正誤判定ロジックなど「ビジネスロジック」中心
E2E Test        : Playwright
                  対象: サインアップ→初回Quest完了までの主要導線、
                  SQL実行→正誤判定、AI Mentorへのヒント要求
Coverage目標    : ビジネスロジック層は目安70%以上。UIコンポーネントの
                  網羅的なテストは優先度を下げてよい
```

- CI（GitHub Actions）で、PR作成時に自動的に `lint → typecheck → unit test → build` を実行する。E2Eは主要導線のみをCIで回し、実行時間とActions無料枠消費を抑える。
- 全チェックがgreenでない限りmainブランチへのマージを推奨しない（強制ブロックはリポジトリ設定次第でよい）。

# 13. パフォーマンス・アクセシビリティ

- Core Web Vitals目安：LCP 2.5秒以内、CLS 0.1未満を目標とする。

## 13.1 ブラウザサポート範囲

DuckDB-Wasm・Monaco Editorはいずれもモダンブラウザを前提とする。以下を最低サポート範囲として定義し、READMEおよびdocs/architecture.mdに明記する。

```text
サポート対象: Chrome, Edge, Firefox, Safariの直近2メジャーバージョン
非サポート  : Internet Explorer（そもそもNext.js/WebAssembly非対応）
```

- サポート外ブラウザでアクセスした場合、真っ白な画面やエラーの連続ではなく、「対応ブラウザでアクセスしてください」という案内を表示するフォールバック（最低限のUser-Agent判定またはWasm非対応検知）を用意する。
- SharedArrayBuffer/COOP・COEP（5.1節）はSafariでの挙動がChrome系と異なる場合があるため、実装時にSafariでの動作確認を必須項目に含める。
